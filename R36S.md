# R36S / ArkOS builds

The R36S (RK3326, Cortex-A35, 640×480) runs ArkOS, whose userland is
Ubuntu 19.10 (eoan): glibc 2.30, GCC 9's libstdc++ (`GLIBCXX_3.4.28`),
SDL2 2.0.10 as the default `libSDL2-2.0.so.0` (newer builds are installed
next to it, see ARK-7). A binary linked against nixpkgs' glibc does not
start there.

## Toolchain

**ARK-1.** Build against a sysroot of eoan arm64 `.deb`s fetched from
`old-releases.ubuntu.com` with their archive hashes (STACK-8), extracted with
`dpkg-deb -x`; absolute symlinks inside are rewritten into the sysroot.
Reference: xanatoo / kurvenrausch `nix/r36s.nix` (`arkos-sysroot`, FLAKE-1).

**ARK-2.** The compiler is nixpkgs' `pkgsCross.aarch64-multiplatform` GCC,
but every header and library comes from the sysroot: `-nostdinc -nostdinc++`,
`-isystem` for `usr/include/c++/9` (+ multiarch, `backward`), GCC's own
`include` only for compiler intrinsics, `-nostdlib++ -lstdc++` against the
sysroot's `libstdc++.so.6`, `--dynamic-linker=/lib/ld-linux-aarch64.so.1`,
`-mno-outline-atomics` (no `__aarch64_*` helpers in GCC 9's libgcc).
No ABI shims are needed then.

**ARK-3.** SDL2 is linked against a stub `libSDL2-2.0.so.0` (sysroot symbols,
empty bodies) so the device's own SDL2 (KMS/DRM, ArkOS build) is used at run
time. Code calls only SDL ≤ 2.0.10 API directly. Newer functions (e.g.
`SDL_RenderGeometryRaw`, 2.0.18) are looked up at run time when
`SDL_GetVersion()` reports a version that has them, through
`SDL_LoadObject("libSDL2-2.0.so.0")` + `SDL_LoadFunction` (plain `dlsym`
needs `-ldl` with glibc 2.30), and the code keeps a 2.0.10 path. Reference:
xanatoo's patched ImGui SDL_Renderer backend, which falls back to drawing
triangles as rectangles and caches the UI in a target texture.

**ARK-4.** Check every R36S build: the highest `GLIBC_` / `GLIBCXX_` /
`CXXABI_` version in `objdump -T` must not exceed what the sysroot's
`libc.so.6` / `libstdc++.so.6` define, and the binary must start under
`qemu-aarch64 -L <sysroot>` (`--version`, `--show-paths`, with the SDL2 stub
on `LD_LIBRARY_PATH`: the real SDL2 pulls ALSA etc., which the sysroot does
not carry).

**ARK-5.** Libraries the device may lack (anything beyond SDL2, FreeType,
Fontconfig, zlib, libpng, OpenSSL 1.1) are added to the sysroot as eoan debs
and shipped in the port's `libs/`; the launcher prepends
`$GAMEDIR/libs` to `LD_LIBRARY_PATH`.

**ARK-7.** Should: the launcher preloads the newest SDL2 the firmware
installs when it is newer than the default link, for the game command only:
`LD_PRELOAD=<newest libSDL2-2.0.so.0.*> ./<game>`; the preloaded library
satisfies the `libSDL2-2.0.so.0` dependency by its soname, so only that SDL
is mapped. No symlinks are written (`/roms` may be FAT). Firmwares whose
default is already the newest are left alone. Reference: xanatoo
`mk/r36s/Xanatoo.sh`.

## The device

Found on one R36S with ArkOS (2026-10-29, xanatoo's startup report,
LOGGING.md):

| | |
|---|---|
| Kernel, RAM | Linux 4.4.189 aarch64, 4 cores (NEON), 897 MB |
| Video | SDL `KMSDRM`, 640×480 @ 61 Hz, `SDL_PIXELFORMAT_ARGB8888` |
| GPU | ARM Mali-G31, OpenGL ES 3.2 (`v1.r13p0`), `/usr/local/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-gbm.so`; SDL uses its `opengles2` renderer (vsync, render targets, max texture 8192×8192) |
| SDL2 builds in `/usr/lib/aarch64-linux-gnu` | 2.0.10 (default: `libSDL2-2.0.so.0` → `libSDL2.so` → `…0.10.0`), 2.0.14, 2.0.16, 2.0.18, 2.26.2, 2.26.5, 2.28.2, 2.30.3, 2.30.7, 2.30.10; 2.30.10 runs fine with KMSDRM and the pad |
| Pad | "GO-Super Gamepad" on `/dev/input/event2` (`js0`); PortMaster sets `SDL_GAMECONTROLLERCONFIG` and `SDL_GAMECONTROLLERCONFIG_FILE`. SDL ≥ 2.26 adds a CRC to the GUID (`1900bb3e…` instead of `19000000…`) but still applies PortMaster's mapping |
| PortMaster | This install's `control.txt` has no `pm_finish` / `pm_platform_helper`, so `gptokeyb` keeps running when the game quits by other means than Select+Start |

Performance: the GLES driver is slow per draw call. ImGui's chrome drawn
with one SDL call per triangle (~2400 per frame) held xanatoo at ~20 FPS;
cached in a texture or drawn with `SDL_RenderGeometryRaw` it runs at the
61 Hz vsync rate. Batch drawing; count draw calls before blaming the CPU.

## Testing on the device

- Over ssh as `ark` (passwordless sudo); stop the frontend first:
  `sudo systemctl stop emulationstation.service`.
- Start the game with the launcher's environment (source PortMaster's
  `control.txt`, `get_controls`, export `SDL_GAMECONTROLLERCONFIG`,
  `LD_LIBRARY_PATH`, the XDG variables pointing at a test directory) and
  `--no-save`, in the background; stop it by its PID.
- `/dev/fb0` is the text console, not the KMS scanout: reading it gives no
  screenshot.
- Input can be injected by writing `struct input_event`s (`llHHi`) to
  `/dev/input/event2` with sudo. The driver keeps reporting the real stick,
  so a held axis must be re-sent every few milliseconds.
- Measure with a frame counter printed to stderr, not by feel; the log is
  `log.txt` in the port directory when started through the launcher.

## C++ standard

Results from xanatoo (2026-10-29, GCC 16.2 cross, libstdc++ 9.2 headers):

| | Status |
|---|---|
| `-std=c++20` compiles and links | **works** (xanatoo, thumtoo off) |
| C++20 language features: defaulted `operator==`, designated initializers, `std::string_view`, `std::filesystem` (in `libstdc++.so` since GCC 9.1, no `-lstdc++fs`) | **works**, binary needs ≤ `GLIBCXX_3.4.26`, starts under qemu with eoan libs |
| `CMAKE_CXX_STANDARD=17` on C++20 code | fails (defaulted `operator==` is C++20) |
| C++20 library headers GCC 9 does not ship: `<span>`, `<ranges>`, `<compare>` (so `operator<=>`), `<concepts>`, `<numbers>`, `std::bit_cast` (`<bit>` itself exists), `<source_location>`, `<format>`, `std::jthread` / `<stop_token>`, `<semaphore>` / `<latch>` / `<barrier>`, coroutines | **not available**: language features that need these headers do not work either. Not tried; from libstdc++ 9's header set. |
| Running on the device | **works** (xanatoo C++20 build on the R36S, 2026-10-29) |

**ARK-6.** A game that targets the R36S may use C++20, but only the
language features and the library parts that libstdc++ 9 has. The R36S
build passes `-DCMAKE_CXX_STANDARD=20`; it fails to compile when code uses a
newer header, which is the intended guard.
